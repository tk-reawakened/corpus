The True Nature of Multirun()
Multirun() is a very interesting command in the TK syntax. It does all kinds of magical things that threads can do, and supposedly if used with threads can precipitate a very powerful effect indeed within your game project. But the TK lags like a mutha! It's difficult to speed things up! How would you use Multirun() effectively, given all the ramifications? This guide is here to tell you how to do that. *possibly*
Part 1: What Multirun() does
Multirun() takes the following format:
Multirun()
// --- Commands go here... --- //
As you can see, this closely resembles a Until(){} or While(){} loop...but it only runs once. Interesting fact, isn't it? And it's not like an If() or Iif() or one of the aforesaid loops in that it dosen't require a boolean argument denoting...well anything. It dosen't even anything! Interesting indeed, huh? *require*
That's because Multirun() is all about or doing something I suck at, personally--two or more things at once. Many would say 'in the TK, that means going slower than a snail with a broken foot.' Though in many cases it is the case, that's also not necessarily true--the key issue with using Multirun(), like using RPGCode in general is code efficiency and understanding what's going on with your code. Multirun() can cause you a lot of unforseen issues because of its seemingly beneficent nature, if you don't know what it does, or what to look out for. *multitasking,*
Part 2: The Clock Example
The following code is for a small clock that constantly updates using the gametime! system variable, and PixelText(). This will use a Canvas as well for smoother execution and no black flicker, so newbies should especially pay close attention to this code, as you find a number of educational things: *will*
// Clock Example Code:
// This code shows a self-updating clock using
// multirun and some text.
done! = 0
timeCnv! = CreateCanvas( 600, 25 )
// --- Show user information... ------------------
PixelText( "System:", 25, 25 )
PixelText( "The below is the time this program has been running in seconds.", 50, 50 )
PixelText( "This should be updating continously. Press [Space] to end this.", 50, 75 )
// --- Main Program Loop... ----------------------
until( done! == 1 )
multirun()
// --- Prepare the next update... ------------
SetImage( "black.png", 0, 0, 600, 25, timeCnv! )
PixelText( CastLit( gameTime! ), 270, 0, timeCnv! )
DrawCanvas( timeCnv!, 0, 275 )
if( userInput$ == " " )
KillCanvas( timeCnv! )
done! = 1
Get( userInput$ )
// --- End Program... ----------------------------
(Please excuse the lack of whitespace above, the WYSIWYG editor didn't want to give me spaces between code segments...you'll have to run off my comments and the code itself as far as readability goes.)
...Where black.png is just a 1x1 png image of a black dot. If you want to, take a screenie and extract the last sentence's period to supply that. Regardless of that, this seems very contrary to usual code, right? Almost to the point of being nonsensical? Let's really analyze it and see what's going on.
First, we enter the code by declaring the LCV, preparing a 640x25 canvas for rendering the time, and we show the text to inform the user of what's going on. Then things get interesting. We enter the program's main loop, a While() loop, mind you, on the condition that if done! ever becomes 1, we're finished with the loop and therefore the program. E nter Multirun(). You see a few commands prepared: The black.png image is set on the canvas again, the PixelText is rendered to the canvas, is evaluated of all things...and then we accept userInput$ for that iteration of the loop. What gives? *USERINPUT$*
Multirun() takes place in real time, and you Instead of doing what you'd do in a cute little conditional loop like While() or Until() where you accept input from the git-go and then process it, in a Multirun() within a loop you must flip the order in which things are done--the past is executed first, and the present is then given time to execute. This is a small sequence thing that seems trivial at first, and you could indeed do it the other way around entirely...with the consequence being that if you hit [SPACE], the clock would update if it's the correct time before it would close, not the other way around, which is what you desire. Of course, Multirun() runs commands at once, right? Why would sequence matter at all? Well...I think the next part is overdue for explanation. *must never forget that fact.* *really*
Part 3: Things to watch out for
Multirun() is very interesting--running multiple things at once is good. So why not create a full RTBS within one Multirun()? Seems good...except for the TK3.0.6's current speed limitations due to executing within MS Visual Basic, and the nature of Multirun() -- it instead splits the Multirun()xor'd commands apart and sequences those parts to make it seem like it's executing at once (the behind to this comment is a key point. Copy it to your desktop. Meditate to it. Make it a church hymn. Do whatever it takes short of homicide to remember this point.) That comment I made after the Clock example? Guess what--even down to the Assembly code level, the same thing happens--things are distributed out to make it seem as if it's all being ran at once, thought the fact is the contrary of that assumption--the computer's worse at doing two things at once only more than I am. The only thing you can really do about this fact is optimize the code within the Multirun() code block to make it execute faster. **true** *running two things at once dosen't cause the system to speed up...*
Among the first things you should never do is use any If() statements or decision making within the Multirun(). Isn't that frigging limiting in terms of what you can do? Forget that battle system, huh? Not really if you use Multirun() within a loop--you do the processing after the Multirun is completed. Keep in mind, though, that Multirun will do ALL of its commands first before giving control to anything else, be it another program or another command. Even the If() block I have in my above example is NOT a very good idea, to be honest--when I ran it here on my home computer, the program lagged a bit at first, but then stabilized rather quickly. The best thing you can do about this is what I said: put processing after the Multirun(). Get() statements and such are game for this section, though you could also use Get() just as effectively outside the loop...really, Multirun() is really keyed for actions, as even the Manual's example program for Multirun() has two NPCs walking together at once. Take a cue from this, and make action be Multirun()xor'd, let the TK do the thinking when the loop iteration is near done.
Another good idea is to use the Kill() statement liberally within any Methods that you may call from the Multirun() block. Kill() removes a variable from memory, and should therefore be used to delete a method's variables--for your Multirun()/Loop() conglomerate, you hopefully don't need whatever was in that method and used to calculate something or other. Killing can be very good for speed, as the system isn't bogged down by extra variables that it won't use, at least not right away.
Whatever you do, don't ready-code some TextBox() method...that has Wait() in it, or worse any loops! Wait() does work within Multirun() as do While() and Until() loops, and will disrupt what you're trying to do! Use Get() inside the loop, and go with what I said in the second paragraph of this part of this article! Again I iterate: do processing after you Multirun()...loops are processing, as they're conditional!
Conclusion
MULTIRUN DER IS NO BLACK FLICKER LOL! Oyerth once said it about something or other on TK Chat, and this command is very powerful--it's no wonder one would comment over it with such great enthusiasm. I just hope you keep the ramifications of this command in mind when you're developing that 1337 Real-Time Battle System...or that in-game clock for your Custom Menu System...whatever it may be you're Multirun()xoring in hopes of 1337ness.
Oyerth was mocking you when he said that. Multirun does not make things run at the same time, as you post occasionally. Its main purpose is for pushing sprites at the same time, although it can also help with lazy thread coding. It does not do the things you seem to think it can do. > This command runs multiple commands inside it's opening and closing brackets. If used in a thread, it's useful for running a block of code without the thread giving control to another program. It can also be used for various other things, like making NPC's walk simultaneously (the commands aren't executed until Trans3 sees the closing bracket).
>
*you*
Obviously if you have doubts about the quality of the documentation, you should raise them before writing an article making a liberal interpretation of it. The documentation is not infallible and it tries (in error) to be "simple": the description of multirun is one of these simplifications. My original goal with multirun was to allow for lazy thread coding without having to create temporary canvases -- this goal was a little bit silly because it can be done a more standard way, but it worked well in 3.0.5 for, e.g., rain effects. In 3.0.7 this feature will no longer exist because it is no longer practical with the new way 3.0.7 handles threads and it requires the user to understand what is going on, which is a bit much to ask. However, it happens that multirun came to take another role even before the release of 3.0.5(4?), to push sprites at the same time. This is what it is really useful for and this is what everybody who uses it uses it for, because, remember, this was added before the version that added multirun was released. Now I guess the documentation wanted to offer a bit of the "mentality" behind multirun and with sprites it literally does not push anything until the closing brace is reached. But in general multirun does not queue execution of its contents. Even if it did, it would function pretty much exactly the same as having no multirun (except in threads, as we've been over) so you still overestimate its power with your metaphysical analysis, even based on misleading documentation. In conclusion, the documentation, in its effort to elucidate The True Nature of Multirun, may have needlessly generalised and simplified, but your interpretation is still quite broad. To be fair, your article applies multirun somewhat correctly in 3.0.6 to the clock example, but the explanation thereof is very misleading and in often wrong (the thread simply does not lose control until multirun finishes -- it is not so complicated as you make it out to be) and the coding technique is dated. All multirun should be used to do is queue movement so that several sprites can be made to move at once.
