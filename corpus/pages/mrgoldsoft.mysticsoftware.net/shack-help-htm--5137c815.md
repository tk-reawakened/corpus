- Arrays -
By MrG
Arrays aren't really that hard to figure out, you just need to be able to connect things together in your mind. First off, make sure you understand how variables work. This isn't a variables tutorial, and we're assuming at least a basic knowledge of their function, how they work, etc. That being said, let's look at a simple array that we all know and love: playerhandle[x]$. In case you don't know, the playerhandle variables store the handles of every player on your team. They're stored in an array. An array is, basically, a collection of variables grouped together in a collection. This is how an array works, in a simple little formula: variable name + [ + reference number + ] + ! or $ Obviously, the variable name is the name of the array, like any old variable name. The "reference number" is how we figure out which variable inside the array we're looking at. There are 5 player handles, right? So we need to put a number in here to tell the program which player handle we want. Finally we have whether the array is a numerical (!) or a string ($) variable. So what's the point of arrays? So far they act just like any other variable, you use playerhandle[0]$ and you get the handle of the first player, no big deal. The cool thing about arrays, though, is that you can use a variable as a reference numbers. This means you can do: #bob!=5 #handle$=playerhandle[bob!]$ And RPGCode will know what you're talking about. You can even use strings for the reference "number" (these arrays are actually called maps, but don't worry about that..) So if you wanted, you could do this: #dog$="puppy" #age!=ageofdogs[dog$]! Pretty neat, no? Arrays drastically cut down your code size and speed up your program, and whenever you're using collections of variables, be on the lookout to see if you can use arrays instead. Here's an example: #If(playerhandle[0]$~="") { #GetHP(playerhandle[0]$,hp0!) #GetSMP(playerhandle[0]$,smp0!) }
#If(playerhandle[1]$~="") { #GetHP(playerhandle[1]$,hp1!) #GetSMP(playerhandle[1]$,smp1!) }
#If(playerhandle[2]$~="") { #GetHP(playerhandle[2]$,hp2!) #GetSMP(playerhandle[2]$,smp2!) } *etc. Ugh. Why do that when you can use a simple little loop instead! (For the sake of simplicity, we'll use a #While loop instead of a #For loop.. ;) )
#playernum!=0 #While(
playernum!<=4) { #GetHP(playerhandle[playernum!]$,hp[playernum!]!) #GetSMP(playhandle[playernum!]$,smp[playernum!]!) #playernum!=playernum!+1
} Much smaller, better, just plain more delicious! Thus concludes our lesson on arrays. Now go out and change all your super huge programs to use these cool things! And be glad you don't have to do it the old way! :D

- Multitasking -
By MrG
Many people are exuberant about the tile animation in 2.20, but what some people don't realize is that tile animation is already possible. It's possible through the TK's limited, but functional multitasking engine. This animation is fairly simple: make an item with no graphics, and for its Program to Run While Item is On Board, put something like this: :top #LayerPut(5,2,1,"fire.tst1") #LayerPut(5,2,1,"fire.tst2") #Branch(:top) And whala, you have a simple tile animation (use your own gfx names and coords of course.) But what most people claim is that this is simply too slow to be worth anything. However, what most everyone does not realize, is that there are things you can do to speed up your multitasking performance. This tutorial will cover some of those methods. First, you have to learn a little of how the multitasking in the TK works. Basically it takes your Program to Run While the Item is On Board (your multitasking program), and runs it one line at a time. Every time it gets a chance (the player stops walking, the other multitasking programs stop for a breather), it runs another line. There are tricks, however, hidden within this engine. - First, make sure your multitasking speed is as low as possible. The "speed" is the amount of time the TK takes between running the game and running your multitasking program. Therefore, you want it to be as low as possible so it runs as quick as possible. Go into the Main File Editor, Project Settings, and move your Multitasking Speed all the way to the left. - Yes, the TK runs multitasking programs one command at a time, but it runs commands with brackets like everything inside the brackets is one command! That means that with something like: #If(bob!=0) { #LayerPut(5,2,1,"fire.tst1") #LayerPut(5,2,1,"fire.tst2") } The TK will run both those #LayerPut commands at once, if bob! is 0. Cool, no? This means that if you have a bunch of animation you want to run, and you don't want to plod along one line at a time, you can stick it in #If brackets, like this, with meaningless variables so you'll be sure it will run: :top
#If(bob!=0) { #LayerPut(5,2,1,"fire.tst1") #LayerPut(5,2,1,"fire.tst2") }
#If(bob!=0) { #LayerPut(5,2,1,"fire.tst3") #LayerPut(5,2,1,"fire.tst4") } #Branch(:top) A word of warning.. Be sure you don't stick everything in one #If, or you bog the game down and give the player less time to walk.. A good rule of thumb is to take the amount of actual commands you have, divide by two, and use that many #If brackets. - It's better if you don't use methods at all in a multitasking program, but sometimes you have to. For instance, if you start getting too many #Ifs inside #Ifs in a multitasking program, the game will slow down considerably. So if you find your big multitasking programs suddenly stop working for odd reasons, check your #If count and see if a method is in store. Well, that's it, but you'll find these little tips and hints can make a big difference in your multitasking performance. Granted, the engine needs work, but with a little tweaking, give it a try and see if you're not a believer!

- Graphical RPGCode-
Written By Stalfospk
*********Graphical Rpg Code Tutorial****** **********Created by Stalfospk********** I. Introduction II. Changing Colors A. Variables B. Effects III. Changing text colors A. commands B. Guide IV. drawrect,fillrect,drawcircle,fillcircle,drawline V. Closing words I. Introduction Welcome friend. The reason you're reading this is either to learn about graphical rpg code, or because you have no life. Either way, I hope you enjoy it. In this tutorial, you'll learn about rpg code and the graphical capabilities of it (that was hard to figure out). II. Changing Colors Let's start with some basics, changing colors and shades in rpg code. Here are the variables for the shades of color: ambientred! ambientblue! ambientgreen! They control the amount of the certain color on the screen. Now, we can go onto changing these for your benefit... Say you want to have a town on fire or something, so you want to give the screen a tint of red. All you'd have to do is: #ambientred!=ambientred!+100 Of course, change the 100 to however red you want it, the larger, the redder it gets. Now, to make a better effect, add this to it: #ambientblue!=ambientblue!-100 #ambientgreen!=ambientgreen!-100 Also, when you want to change them back, just do this: #AmbientRed!=AmbientRed!-100 #AmbientGreen!=AmbientGreen!+100 #ambientblue!=ambientblue!+100 I hope that helped you with shading colors. III. Changing Text colors To change the color of text made form the #text command, just type #color(color!) before the #text command. Replace color! with a number from 1-15. Any number after 15 will show up black. Now, here's a list of the colors for you: 1=blue 2=green 3=teel 4=red 5=purple 6=brown 7=grey 8=dark grey 9=light blue 10=light green 11=very light blue 12=light red 13=pink 14=yellow 15=white 16+=black There, now you won't have to experiment to find the color you're looking for. That should do it for changing text colors... IV. The Draw commands So far, you've learned the basics of colors,etc., but here's where the real graphical programming is. I'll introduce 5 commands to you and teach you how to use them: #drawrect(x1!,y1!,x2!,y2!) This command draws a rectangle from the the variables you give it. It uses the current color that is being used. To change this, just use the #color command you learned earlier. #fillrect(x1!,y1!,x2!,y2!) This command does the same as #drawrect, but it fills in the rectangle with the current color. #drawline(x1!,y1!,x2!,y2!) I think you can figure out what this does #DrawCircle(x!,y!,radius![, startangle!, endangle!]) This draws a circle like #drawrect draws a rectangle. The last two variables in it are optional. #FillCircle( x!, y!, radius!) Does what #fillrect does,but with a circle. Those commands are very helpful if you're "artistically challenged" like I am... That does it for those commands... V. Closing statements Well, I hope this short tutorial helps you understand the basics of graphical rpg code. - Custom Commands-
Written By Don't_Think_So
This tutorial teaches you how to create custom commands that can be used anywhere, as if they were regular commands. Here is an example that uses three sets of custom commands: #mycommands.glowtext(12,14,1,5,"test") #myotherprghere.blah(1) #someotherproggiehere.ummm(grrr) #thisismyotherproggieofassortedmiscellany.doesn't_this(stink) #wait(a$) Now, you can see how this can get very tedious. Well, with this rather short tut, this will be no more! It is very very very simple. Just #redirect all of your custom commands in your start program. I put it right before it draws the title screen. Here is how it goes in my game: *my custom commands | name of | where the * V new command V method is #redirect(#glowtext,#mycommands.glowtext) #redirect(#randomrange,#mycommands.randomrange) #redirect(#pause,#mycommands.pause) #redirect(#redshade,#mycommands.redshade) #redirect(#greenshade,#mycommands.greenshade) #redirect(#blueshade,#mycommands.blueshade) #redirect(#yesno,#mycommands.yesno) #redirect(#charcount,#mycommands.charcount) #redirect(#findstring,#mycommands.findstring) #redirect(#toggle,#mycommands.toggle) #redirect(#drawbar,#mycommands.drawbar) #redirect(#bossbattle,#mycommands.bossbattle) #redirect(#time,#mycommands.time) #redirect(#slowzoom,#mycommands.slowzoom) #redirect(#virtbutton,#mycommands.virtbutton) #redirect(#virtcheck,#mycommands.virtcheck) #redirect(#virtclear,#mycommands.virtclear) #redirect(#fp,#mycommands.fp) #redirect(#dp,#mycommands.dp) *end of custom commands Now, all of my custom commands can be used as normal. Meanwhile, on another program: #glowtext(12,15,5,1,"Isn't this better?") #redshade(1,5,"because i think so") #greenshade(5,5,"wouldn't you agree?") #yesno(maybeso!) #if(maybeso!==1) { I thought you would } #if(maybeso!==0) { Really? Then you shouldn't be reading this tutorial. } #wait(a$) See, isn't that better than having to remember all of those #include commands at the top of every program? - Modified Commands-
Written By Don't_Think_So
If your like me, then maybe at some point or another you have wanted to change a command very slightly, like if you wanted to know the current font size, you could look at a variable (say fontsize!) that was automatically stored with the #fontsize command. So, maybe you want something like this: #mwin("The current font size is !") #prompt("What would you like it to be?",picksize!) #fontsize(picksize!) #mwin("Here is font size
. Do you think it is better?") As you could see, this has quite some ability. For example, you could make a #save command that doesnt save cheats. Ok, now do I have your attention? Good. So, we start by making a method. Following our #fontsize command... #method modifiedfontsize(size!) { #fontsize!=size! #killredirect(#fontsize) #fontsize(size!) #redirect(#fontsize,#mymodcommands.modifiedfontsize) } Now, most people would, at this point, take you step-by-step through this bit of code, but I think your smart enough to know that it basically puts the variable size! into fontsize!, then runs the command as normal, through the #redirect and #killredirect commands. If you are lost, here is another example: #method modifiedsav(destsave$) { #if(cheathpmod!=1) { #givehp("You",-900) *this assumes that you made a cheat that gave you 900 health, and it only *worked once. } #killredirect(#save) *gives the toolkit the ability to use the normal command #save(destsave$) *uses the normal command #redirect(#save,#mymodcommands.modifiedsave) *makes the toolkit run through this same process next *time. } Just read the comments. You'll understand. -Dont_Think_So
