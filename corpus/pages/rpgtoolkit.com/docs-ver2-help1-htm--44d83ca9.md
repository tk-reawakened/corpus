Introduction
Welcome to the RPG Toolkit Development System, Version 2.0! This new version is built upon the same concepts as version 1.4, so a seasoned user of the Toolkit should have no problem adjusting to the new interface. And for the new user, Version 2’s new graphical interface should be quick and intuitive to learn.
The RPG Toolkit Development System is a Role Playing Game editor, which allows you to create your own RPG games with no prior experience or programming skills. It is extremely flexible and allows for an infinite variety of gameplay. Since it keeps a minimum of information in memory while it’s running, the size of a game is limited only by the available hard drive space on the computer you are using. A game created with the Toolkit can range from a very simple 10 screen demo to an immensely complex world in which dwells hundreds of characters, enemies and heroes, all of which can interact with the player.
Version 2.0 is a complete code rewrite- entirely from scratch. It features 16 million-color support for photo quality graphics, 640x480 SVGA resolution, infinitely expandable multimedia capabilities, and much, much more! It is almost entirely reverse compatible with Version 1.4 file formats, so you can port games you have already created from Version 1.4 into the new interface.
The system requirements for this program are as follows:
-Pentium class computer or equivalent (I’d say at least a P133, but it may run on slower machines. The only stipulation I make is that you DO NOT use one of the old x86 class computers, because it is much too slow).
-32MB RAM
-Windows 95+
-A creative mind (theoretically you already have one of these).
Much work has gone into the development of this new Version, and I sincerely hope you enjoy it. As always, I am open to suggestions for improvements and changes. You can email me at (redacted: email), or just visit the RPG Toolkit homepage (http://rpgtoolkit.pyar.com).
Christopher B. Matthews
RPG Toolkit Online

The Fast Track To Making an RPG
This manual is designed to step you through the process of creating your own RPG. It will take you into every detail of designing a game, and once you’ve read it through, you should be able to create a really cool game.
If you want to just know the basics for now, you can create a very simple RPG. The minimum of things you must do to create an RPG with the Toolkit are:
>
> Create at least one board and set the initial player position (see the Board Editor section)
>
> Create at least one character with a full graphic set for walking (see the Character Editor section). . *You can use one of the included characters for now if you don’t want to make a new one*
>
> Create a Main File with the following information: The Menu activation key, the initial board file, and the initial character file. See the Main File section for info on this.
>
> Run the game with the trans2.exe program. See the section on trans2.exe for info on this.
>
If you do these four things, you’ll have a basic game where the character can walk around. You might want to do this first just to get a basic feel for the Toolkit, and then follow the manual step by step to see exactly how to make an RPG. Have fun! *in-depth*

Follow the on screen instructions to install it. NOTE: Icons will only be created in your start menu and desktop if you install to the default directory, so you may want to do this!
Once the program is installed, double click on the Toolkit icon on your desktop, and you’re ready to go!

***
Tiles in the RPG Toolkit
Games that you make with the RPG Toolkit are, for the most part, what are referred to as games. What this means is that nearly every graphic you see in that game- from a town scene to your character’s graphic- is made up of one or more . *tile based* *tiles*
A tile is just a little square graphic that you put together with other tiles to create a larger scene. Since every graphic is made up of tiles in your game, tiles are the core of every game you make. How your game looks depends entirely on the style of tiles that you create.
In the RPG Toolkit, a tile can be a graphic made up of 32x32 pixels or 16x16 pixels. Enough definitions. Let’s make some tiles.
***
Colors and Pixels
No matter what anyone tells you, the most important thing any computer game can have is LOTS of colors. You can have high resolution, ultra fast 3d, whatever, but without lots of color, it doesn’t look real. The Toolkit supports 16 million colors- that is more than enough to reproduce photographic quality graphics.
When you enter the Tile Editor window, you will see a large white box on the left. This is called the , and it is here that you create your own tiles. To the bottom right of the window is a smaller box. This is the , and shows you what your tile looks like to it’s proper scale. *Tile Form* *Image Box*
![](Image388.jpg)
Before we do anything, click the "Grid On/Off" button once to turn the grid on for the Tile Form. Notice that the grid divides the Tile Form up into 32 x 32 squares. This is a larger representation of the tile itself, which is 32 x 32 pixels in size.
![](Image389.jpg)
Click on the large colored bar on the bottom of the window. This provides you with quick access to lots of colors. When you click on a color in the Color Bar, you are selecting the color you want to use in the tile creation. *Color Bar*
Once you have selected a color from the Color Bar, go ahead and click anywhere on the Tile Form. Notice that the color you selected gets put on the Tile Form (and also on the scaled down Image Box). This is basically how you make tiles- just draw things on the Tile Form using different colors.
For now, just draw a simple figure or a scribble or something, so you can get the feel of the Tile Editor.
***

However, if you’re interested in being a and using the Tile Editor to it’s fullest potential, the next section is for you! Remember- tiles are the backbone of your game. If you make awesome tiles, you will have awesome graphics. *power user*

Advanced Features
Like I said, the Tile Editor is really simple, but you probably want to use some of the better features that will make your tiles really good. A good place to start is color...

Ways of Selecting Color
Apart from clicking on the Color Bar to select colors, you may wish to select a very specific color that you just can’t pinpoint on the Color Bar itself. There are three other ways of selecting color in the Tile Editor. You can find them under the menu at the top of the screen. *Color*
The first way of selecting a color is . Select this from the Color menu. This opens a new window with three sliding bars. **RGB Defined**
![](Image396.jpg)
This window allows you to select a color by mixing different intensities of Red, Green and Blue. By sliding the Red, Green and Blue sliders around, you can adjust the levels of each color component. All colors can be created by mixing red, green and blue (white is a mixture of all three at maximum intensity, black is the lowest intensity of all three, purple is an equal level of red and blue, etc). By moving the slider, you can shift all three sliders to lighten or darken your current color. *Slide All*
![](Image397.jpg)
The next way of selecting a color is . Select this from the menu. This opens up a window that gives you a palette of 256 colors. This is the standard DOS palette used by version 1.4. You can select a color by clicking on it, or by entering the color value in the box to the left (just like version 1). **DOS Palette** *Color*
![](Image398.jpg)
The third way of selecting a color is by choosing from the menu. This opens up a new window which lets you choose a color from a pre-set palette, or define your own. It’s pretty self-explanatory. **Select Color** *Color*

Color and Detail
By default, all tiles you create are 32 x 32 pixels in size and use 16 million colors. If you are a version 1.4 user, you will know that version 1 uses 16 x 16 sized tiles with only 16 colors. Well, if for some reason you think that looks cool, you can change the color depth and detail of your tile by playing with the detail and color depth switches on the top right of the window. When you reduce the detail or color, it is a permanent change, so don’t just do it haphazardly.
Often you can reduce the color of an image to 256 colors without much change. You may want to do this because a tile that uses only 256 colors takes up less disk space than one that uses 16 million colors. I don’t really push it though, because you can get the image quality from a tile with 16 million colors, and if the file size is a little bigger, who cares, right? You might want to reduce the color depth to 16 colors if you are especially crazy about disk space, but the tiles won’t be pretty! *best*
Reducing detail, though, can actually come in handy. I find that it’s good to start a tile off in 16 x 16 mode, draw the basic image and then increase the detail to 32 x 32. Once the detail is increased, I round out the edges and touch it up. This saves of time when you’re making a bunch of tiles. *a lot*
If you are going to be opening tiles from a game made with version 1.4, you can increase the detail and color depth of the tile and spruce it up a lot. You don’t have to change tiles made by version 1.4, though. Version 2 can handle them just fine when it comes down to using them.

Nifty Tools
Under the menu are a bunch of really useful tools. You can Flip and Rotate your tile directly from the Tile Editor, which is really useful when making characters and other things that are symmetrical. (In case you haven’t figured it out, you flip and rotate the image using the and commands from the menu). *Tools* *Flip* *Rotate* *Tools*
This can come in really handy when you are making a series of tiles that make up a larger image. For example, let’s say you were making a bunch of carpet tiles. Well, you could draw the northwest corner of the carpet and then save it. Then you’d just have to flip it to get the northeastern corner, and then you could rotate it to get the other two corners. This saves a lot of time, and you will quickly become addicted to it after using it.
The option allows you to skew the tile by slanting it on a 45-degree angle. It skews horizontally from left to right. If you want to skew in another direction, you can flip and rotate the tile first, and then skew it. Skewing is useful when creating 3d corners. For example, let’s say you have created a brick tile. You can skew that tile so that it’s skewed vertically from top to bottom and bottom to top to create two corners. This looks really good when these tiles are used in games (i.e. the towers of the castle in the demo game uses this). *Skew*
The option allows you to convert a graphic (BMP, GIF, WMF or ICO) to a tile. When you select from the menu, a new screen opens up and asks you to select a filename. Simply choose a file and hit the ‘Import’ button to import the graphic. This method is good for importing pre-sized graphics (32x32). If you need to import an image that hasn’t been properly sized, you’ll have to use the option. After you import a tile, hit the ‘Redraw’ button in the Tile Editor to show the new tile. *Import...* *Import* *Grab*
The option is very similar to the import option. It allows you to import graphics ripped straight from a picture of any size. When you select , a new window opens up with a button that allows you to select a graphic first. Just use this to load the file of your choice, and it will be displayed in the window. Now, you have to specify of the image you want to grab. You do this by clicking on the image itself. Click once to define the top left hand corner of the tile, and click again to define the bottom right hand corner of the tile. A blue box will be drawn showing you the selected area. Next, hit the ‘Grab Tile’ button. The image will be captured, and you will be taken back to the Tile Editor. Hit ‘Redraw’ in the Tile Editor to se the new tile. *Grab Tiles* *Grab Tiles* *what part*
Probably one of the most useful tools, allows you to blend two tiles together into one. Let’s say you were making a Tree tile. Now, obviously, the tree will have grass behind it. But you have a separate grass tile made, and you don’t want to have to draw it over again when you draw your tree. Well, takes care of this. Here’s how: *Layer Tile* *Layer Tile*
First, draw your tree tile. Make sure you leave the white area white. The white areas in the Tile Editor represent the ‘transparent’ area of the tile (unless you actually put the white color over it). Once your tree has been drawn, save it. Next open up your grass tile. Now, if you select from the menu, you will be taken to a new window. *Layer Tiles*
In this window, you can select the filename of the tile you want to Layer on top of the currently opened tile. So, select your tree tile. And now hit ‘Layer’. The tree tile will be placed over top of the grass. If you hit ‘Redraw’ in the Tile Editor, you will see this.
Another option in the window is ‘Transparency Layer’. If this is selected, then the two tiles will be blended together by mixing their colors. Try it! *Layer Tiles*
The option simply applies texture to your tile. For example, when you draw a grass tile, you’ll probably just fill the screen with a color of green. Well, really grass is not flat green. By texturizing it, many shades of green will be placed on the image. Using in conjunction with can help you create very realistic looking tiles. Most tiles in the demo game were created this way. *Texturize* *Texturize* *Blur*
The option just makes the tile slightly blurry. One word of caution, though: It will destroy all transparency information, so if you want the tile to have transparent portions, don’t blur it! *Blur*
The option allows you to apply shadows to the tile. When you select this option, a new window opens up with your tile on it. This window allows you to specify where obstructions on the tile are located. An obstruction is anything that doesn’t allow light to pass through it, so when the light is applied, the obstructions will cast shadows. *Light Source*
You can define the areas of obstruction simply by clicking on the tile itself. The areas of obstruction will be highlighted.
Next, you can specify the source of the light and direction. Clicking on the ‘Light Source’ circle to the left does this. The longer you make the line, the longer the shadows will be. When you’re ready to cast the light over the tile, hit ‘Apply Light’. Then hit ‘Redraw’ in the Tile Editor to see the new tile.
The last option in the Tools menu is . This takes you to a new window that lets you turn file compression on or off. Compression can significantly decrease the filesize of your tiles. This only works well if there are few colors in your tile, though. If there are many colors (as the result of importing graphics, texturizing or blurring), you should turn compression off. In this case, turning the compression will actually make the file smaller. *Compression Options* *off*

Tilesets
The RPG Toolkit has two different ways of saving tiles. So far, you have been using the default, called .gph saving. This type allows you to save individual tiles in filenames with a .gph extension. This is ok, but if has a few drawbacks:
>
> >
> > >
> > > The .gph file format is large. One tile can be as big as 11kb.
> > >
> > > You will end up with hundreds of tiles in your \Tiles\ directory.
> > >
> > > You will have to remember all of the filenames for these tiles.
> > >
> >
>
To fix these problems, a new file format was introduced in Revision 4, called the Tileset (.tst) format. The new Tileset format has the following advantages:
>
> >
> > >
> > > The format is very small. It can be nearly 4x smaller than the .gph format.
> > >
> > > You can put many tiles into one .tst file, so your \Tiles\ folder won’t get crowded.
> > >
> > > The .tst format is . When you open a tileset, a window is opened showing all the tiles in the file. To choose one, you just have to click on it. You don’t have to remember hundreds of filenames. *visual*
> > >
> >
>
So, hopefully I have you convinced that you shouldn’t be using the old .gph style anymore. Using the new tileset format is very easy. Here’s how you do it…
It works almost exactly like regular loading and saving of tiles. When you save a tile, though, add a .tst extension to the end of your filename. Your tile will be added to that specific tileset (it’s ok to save more than one tile into the same file, because the .tst format can contain as many tiles as you wish).
When you want to load a tileset, just type the filename, and add .tst at the end. This will pop up a window showing you all the tiles in the set, and you will be able to click on the one you want to open. It’s really easy, and it’s a lot faster than using .gph tiles.
Do yourself a favor. Use tilesets!!! Things will be much easier and faster for you. Also, any tiles that I release on my website are now stored in the .tst format. I am hoping to retire the old .gph format as it is no longer needed. You should try to do the same. On a final note, if you want to save all of your tiles into the .tst format, use the ‘Tileset’ option in the main menu. You can flip ahead to the tileset section of this manual, too.

Edit Board
![](Image399.jpg)
The next most important option is the Board Editor. It is here that you actually get to use your tiles and create scenes for your game. So, the first thing you want to do is select "Edit Board" from the Main Menu screen. This will open up the Board Editor window.
What is a board? Well, basically, it’s just one screen in your game. Each board is a different ‘room’ in a dungeon, or it can be part of a much larger map. Basically, boards are what your player walks on and moves through throughout the game- all your boards together make up the game ‘world’.
So, let’s make our first board. You will notice that the board editor has a large white area. This is the Board Form- and this is where you will see your board that is in progress. Below the Board Form is a bunch of buttons that let you do many things. Well, here’s what they do...
***
Laying Tiles
Before doing anything, you may want to do two things: first, click on the "Grid On/Off" button to turn the board grid on, and also hit the "Draw Lock" button to make sure you’re in draw mode...
The first thing you’ll want to do is select a tile to draw with. Do this by clicking on the ‘Select Tile’ button at the bottom of the screen (the more lazy of you can just hit the ‘s’ key on the keyboard). This will open up a file selection window that lets you select the filename of the tile you want.
![](Image400.jpg)
You can open up one of the tiles you just created, or open up one of the pre-made tiles that came with the Toolkit. In either case, once you open the tile of your choice, you should notice that the tile you just selected will be displayed in a little box in the bottom right of the screen, just below the Board Form. This box shows you your currently selected tile.
Now that you have a tile selected, just click on the Board Form, and the tile will be laid down on the board. That’s all there is to it! Just continue to lay down tiles to create a scene. You can select other tiles as well and use those, too. If you play your cards right, you can make very detailed screens only using a few different tiles!
Here’s a good tip: if you are using tilesets instead of individual tiles (I recommend that you do), you can hit the ‘L’ key to open up the last tileset you had opened. This speeds things up considerably.
***
Tile Types
OK, cool guy, you’ve made a nice looking little scene, but now what? Well, first of all, you may think you’re done, but you’re not. There are a few more things you have to do to make a complete board. First of all is to set the Tile Types of each tile on the board.
![](Image401.jpg)
Notice the "Tile Type" button at the bottom of the screen. There’s also a little "Toggle" button (Both buttons do the same thing). Beside the "Toggle" button is some text that should say "Current Tile Type: Normal". That means that all of the tiles that you just laid down were of type "Normal". That means that the player can walk over top of any of those tiles just as if they were the floor. But hit "Toggle" once. You’ll notice that now it says: "Current Tile Type: Solid". It takes longer to draw many tiles of different shades, so if you are making shadows, try to keep them all at -30, or some other constant level. Not only will it look more realistic, but your boards will draw faster as well.
Using the ‘Ambient Light’ slider bar is good for most lighting effects, but occasionally you will want to add different colored light and other effects to the board.

Layering
The RPG Toolkit allows you to make use of up to 8 board layers. What’s this all about? Well, basically, a board is not limited to merely one flat surface. Rather, you can think of a board as being a three dimensional surface, with 8 levels of height.
So far, we have been working exclusively on layer one. However, there may come a time when you wish to use more layers on your board. When would you do this? Well, let’s say that you make a board that is a jungle scene. Perhaps you would like your player to be able to climb a tree and walk about on the branches above the rest of the board. So, you could use the layering feature to accomplish this.
Layering can be used for many more things, though. These range from blending graphics to creating ‘airships’ that your player can use to fly above the landscape.
![](Image408.jpg)
Let’s start with the simplest application of layering, though—using it to represent multiple levels of height on your board. First of all, you will have to create a board on layer 1. Once that’s done, change your tile type to ‘Stairs to layer 2’ and lay down that type on a certain tile.
Now, when your player steps on that tile, he or she will be transported onto layer two. This just means that the player will no longer use the tile type restrictions that are found on layer one—instead, he will use the restrictions placed on layer two.
OK. So now you have created a way for your player to actually get onto layer two. Now, notice the drop down box at the bottom right of the board editor that says ‘Layer One’. Change this to ‘Layer Two’.
If all went well, the screen should go white. Don’t worry! Your board hasn’t been erased! You are now looking at layer two, which has nothing on it. If you want, you can switch back to layer one to see that I’m telling the truth.
Anyway, now that you are on layer two, you can edit it much as you would layer one. However, before you do this, it is a good idea to hit the ‘Draw all layers’ button. This will make layer one visible to you while you edit layer two.
![](Image409.jpg)
First things first—change the tile type to ‘stairs to layer 1’ and place a tile with this type in the same location as that stairs you placed on layer 1. Now, when your player is on layer one, and steps on the stairs, he will be transported to layer two. When he steps on the stairs again on layer two, he will be transported back to layer one.
The second layer should just be something like a ledge—something that hangs over layer one and which the player can walk on. It would be stupid to fill up the screen so as to completely obscure layer one. Also, around the edges of the ledge, you should make solid tiles so that the player doesn’t walk out into empty space, which will give the effect of ‘walking on air’.![](Image410.jpg)
When you are done with layer two, you can hit ‘Draw all layers’ to see how the whole thing looks.
This is the most basic use of layering, and it is quite useful. However, there is another little trick that you can use layering for that will reduce the amount of time you spend drawing tiles. This is something which layering was never really designed to be used for, but it works, and a number of games on the internet have used this little trick…
Let’s say that you are drawing a scene on which there are grass tiles, but there are also trees that have grass behind them. In order to give the desired effect of having the grass underneath the tree, you blend the tiles together with the ‘Layering’ option in the Tile Editor. However, there is a better way. *could*
What you can do is lay down the grass tiles on layer one, then switch to layer two and lay down the tree tiles over top of the grass tiles. As long as the tree tiles have transparent portions, you will see the grass through the trees. When you hit ‘draw all layers’, you will see how this works.
An important note: make sure that you set the tile type of the grass with the tree tiles above it to ‘solid’, otherwise you character will walk the trees. *underneath*
Also, if you are putting the trees over more than one type of tile on your board, you will have to use some more trickery to make it work properly. Let’s say you had grass and dirt on your board, and you wanted trees on top of both. You have to change the lighting effect slightly between the trees on the grass and the trees on the dirt in order for them to draw properly. This is because the Toolkit will make a blind copy of the tree tiles over the whole board, grass and all. If you set the tree tiles that are on top of the dirt to ambient light level 1, it will force the Toolkit to redraw the tree tile over the dirt, and it will be barely noticeable to the eye.

Player Stats
Aside from a nice set of graphics that move around your screen, the player is a creature that contains a lot of information. After all, the player can fight, move around, talk to people, etc. How can we determine how strong he or she is in a fight? How can we determine how healthy he or she is? Well, on the main window of the Character Editor, we can set up the most important part of the character—the statistics. Don’t shy away in fear. This is actually quite painless.
Really, you only have to do a few things to set up the statistics of the player. First of all, type the player’s name in the ‘Character Name’ field. Notice that all the other fields will change too. This is because they are all set to ‘default’. It highly recommend that you leave them at their default values. There was dark time, in the days of version 1, when you had to manually keep track of the player’s stats. These days, the Toolkit can handle all of that automatically.
Anyway, a bunch of things were just filled into boxes for you. These are . They can be accessed and changed with RPGCode commands. If you are interested in this, skip ahead to the RPGCode section. Otherwise, don’t worry about it—you don’t have to know anything about RPGCode to create a character. Like I said, it’s all automated now. *variable names*
Now, all you have to do is fill out a bunch of initial values. These are values that the player will have when he or she first joins the game. The first option is the starting experience value (XP). In an RPG, is a measure of how many fights the player has been in. As the player fights more and more and gets further into the game, the experience level also increases. The experience level can be used to determine if a player can do particular moves, and it also determines when the player’s skills are upgraded. You can probably leave this value at zero, since the player has had no fighting experience when he or she starts the game. You can, however, change this if you wish. You may wish to if this is a player that joins the game far into the story. Generally, these characters start with a higher experience to match the other characters in the game. *experience*
The next value to fill out is the Starting Health value (HP). Each player has a health level—when that level reaches zero, the player is dead. So, in a fight, the higher the level of health that a player has, the better off he is. For a beginning character, 100 is a nice round value to start off with. Following this is a Maximum Health Value. You should probably set this at 100 as well. The maximum health level ensures that a player starting the game doesn’t get a health of 99999999999, or something, which would make him virtually invincible. The maximum health increases as the player’s experience increases.
Next is the Defense Value (DP). This is a value, which determines how well a character can defend himself. For example, if an enemy attacks the player with an attack level of 100, and the player has a defensive level of 40, then the player will only suffer 60 damage. At the start of the game, a small number like 10 is appropriate.
Next is the Fight Value (FP). This is the value that determines how powerful the player is in a fight. If the player attacks an enemy and has a fight value of 200, and the enemy has a defensive value of 10, then the player will inflict 190 damage on the enemy. For the start of the game, a value like 60 is good.
Next is the character’s special move power level. This determines how much special move power (SMP) the player has. The special move power is required to do special attacks, like magic attacks or healing moves. The more SMP a player has, the more he or she can use these special moves. A good starting value is 50, but if the player is a key magic user, then the value should probably be higher. Also, you must fill out the maximum SMP value. This is similar to the Maximum HP value.
Finally, you have to specify the player’s initial level. Level 1 is a good starting point. As the player builds experience, the will increase. Each time the level increases, the max HP, max SMP, FP, and DP also increase. For a player at the start of the game, like I said, a value of 1 is good. For a player that joins the game later on, a higher value would be appropriate. *Level*

![](Image414.jpg)

Setting the players level attributes sort of goes hand in hand with the player stats. But it’s a little simpler. When the player’s experience increases, it makes sense to reward the player with power ups of health and fighting power. As already discussed, that is what levels are for. When the player reaches a new ‘level’ of development, his or her hp, dp and fp increase. If you click on the ‘Levels’ button in the Character Editor, a new window will pop up.
There are some important things in this menu. First of all is the ‘Initial Experience Required For Level Progression’. This is the amount of experience the player must gain before progressing to the next level. If the player starts off at level 1, a good value for this is 100. This means that the player will have to gain 100 experience points before progressing to level 2.
The box that defines what the increase in the required experience is also very important. As the game progresses, each enemy should give progressively more experience (because they are more difficult). It wouldn’t make sense if an enemy gave the character 1000 experience, and the player always needed 100 points to progress—the player would increase by 10 levels every battle! In order to offset this, the experience required for progression should increase as levels increase.
The value you specify here is the percentage by which the required experience increases from one level to the next. In other words, if you set this value to 10%, and the initial increase amount is 100, then once the character has made it to level 2, the experience required to get to level 3 will be 110 points. Then the experience required to get to level 4 will be 121, etc. A value like 10 is good. The default 2% is also good, but it may allow level progression to be too quick. Really, this depends upon the length of your game. The higher you make the number the longer your game will have to be to balance the extra time required by the character to progress his level.
Next you can specify what the maximum level is. The player can’t increase forever, otherwise you might have an invincible character! 99 is used by most RPG games.
Finally, you can specify the percentage by which the max hp, dp, fp and spc power increases when the player reaches a new level. A value like 10% is good for this. A word of caution: make sure the percentage is high enough to actually make a difference. For example, let’s say the player’s hp was 60, and it was to increase by a measly 1% when the level increases. 1% of 60 is 0.6 points. The Toolkit will round this down to 0. So the player’s health will NEVER increase! If the value is set to 10, then the player will go from 60 hp to 66 hp when his level increases. Much better!

Edit Enemy
Now we move into the darker realms of the RPG. The enemy. So far, we have created a character, decked him out with all the necessities for a big fight. But what has he been preparing for? Well, it’s time to create his worst nightmare…
An RPG is not about fighting. RPG’s generally are more of an ‘interactive story’. Fighting is a large part of that, but it is not the central feature as in most action games. An RPG’s fighting system is what I call ‘passive action’. Whereas in an action game, the player is forced to fight because an enemy is coming towards him, in an RPG, the player is usually ‘attacked’ by organized parties of enemies. You don’t see the enemies coming. Rather, when you are attacked, you are swept away to a battle screen where the fight occurs.
In an action game, there is very little strategy. Usually, your goal is to whip out your biggest weapon and load your enemy full of bullets. In an RPG, a fight is far more strategic. While in an RPG, you rip an enemy to pieces with an especially powerful move, this is usually not done because the players need to conserve their energy. Fights occur in groups—there are usually a team of enemies and a team of good guys. Each individual in each group generally has its own specialties. *can*
Enemies can be very diverse in the Toolkit. They can range from a wimpy little rat to a madman with the power to destroy the earth. And size doesn’t matter. Why not give the rat the ability to destroy the earth? The player wouldn’t see that coming!
Creating an enemy is very similar to creating a character. The only difference is that the computer controls an enemy, and since the player is only concerned with the enemy until it is dead, there is no need to bother with things such as level progression and such with an enemy. In other words, an enemy is a flash in the pan. While you may encounter the same enemy more than once, it never gets more powerful, like your characters do. The issue of enemy strength is dealt with as your character moves from one area to another. At the first of the game, the enemies should be fairly easy. As the player moves out into the world, the enemies should be more difficult.
In the final cave or dungeon, the player shouldn’t encounter enemies from the start of the game. When the player moves to a new area, the old enemies stay there. So, the player is always encountering new enemies. Which means we have to make lots of enemies. And that’s what the enemy editor is for.

So far, I’ve talked a lot about RPGCode programs. And you probably don’t know anything about RPGCode. Well, now it’s time to get your feet wet.
First things first: what is RPGCode? Well, it’s a programming language that you can use to get into the guts of the game and do pretty well whatever you want. Wait!!! Before you go and throw this guide away, please—don’t be afraid of that term ‘programming language’.

Commands… and Stuff
The way a programming language works is by giving the computer . The computer will do whatever you tell it to. Go ahead and let that power go to your head, it’ll make you feel good. *commands*
In the RPGCode language, each line of text you place in the RPGCode editor is considered to be some form of a command. For example, please type this in the Editor:
#Mwin("This is a command")
OK. Now you’ve got one command laid down there. So what? Well, let’s see what it does. If you look at the menu bar up to, you will see a selection entitled ‘Run’. Drop that down and select ‘Run’ from the menu (or, just press F5. I’m sure you’ll get lazy like me and just hit F5 all the time). Now wait…
And wait… Your little RPGCode program will be launched. And what will happen? You’ll probably wait for about 10 seconds while it loads, then you’ll see the text ‘This is a command’ flash before you for about one second then disappear. Then you will be back… Sort of like an out of body experience, eh?
Well, here’s exactly what happened…
>
> >
> > >
> > > >
> > > > >
> > > > > You hit the ‘Run’ command. This launches trans2.exe, which will run your program.
> > > > >
> > > > > When trans2 is started, it will begin to run your program.
> > > > >
> > > > > Trans2 will look at our program and see the first line--#Mwin("This is a command")
> > > > >
> > > > > Trans2 will ‘execute’ (run) that command.
> > > > >
> > > > > The command #Mwin puts text in a window called the Message Window. In this case, the text is ‘This is a command’.
> > > > >
> > > > > That text gets out in the ‘Message Window’.
> > > > >
> > > > > Once the text has been printed, trans2 shuts down and returns you to the RPGCode editor.
> > > > >
> > > >
> > >
> >
>
Not too bad. Basically, the computer interpreted your command and did something. Your command was #Mwin. As it is, that command opens up the message window and puts text in it. Isn’t that what happened?
Now, here’s a problem—the text just flashed in front of you. No real time to read it, right? Well, you can add another command to your program...
#Wait(a$)
Just put that directly after your first command. It’ll cause the computer to wait for the user (you) to press a key before clearing the message window and shutting trans2 down.
So, now you can put text in the message window with the #Mwin command and force the computer to wait for you to press a key with the #Wait command. If you are really curious as to what the a$ is in the #Wait command, you’ll have to flip ahead to the RPGCode section for a full explanation.
***
Putting a program to work
OK. What’s the purpose of an RPGCode program? Well, you can basically interact with the player through an RPGCode program. For example, let’s say you wanted to put an old man on a board, and you wanted him to say something to the player when he walked up to him. Here’s a little program to do this:
#Mwin("Old man: Hi. Isn’t this RPGCode stuff great?")
#Mwin("Player: What are you talking about?")
#Wait(a$)
Now you can save this program. Let’s say we save it as oldman.prg. Now, how do we put this program on a board? To do this, you have to go into the board editor. Lay down a tile somewhere that looks remotely like an old man. Now go up to the RPGCode menu and select ‘Set Program’. Now you can click on that old man, and a box will open up asking you what filename to use. Select ‘oldman.prg’. Now save your board. Ta da! That’s it! Now, when you play the game and the player steps up to that old man, the file oldman.prg will be run, and the above text will be displayed. Easy, no?
This is how you set any program on the board. And a program doesn’t have to be as simple as the one here. It can be interactive, and receive input from the player. It can display a story sequence. It can do pretty well anything. RPGCode is powerful, and there’s very little you can’t do with it (with regards to an RPG, that is).

If the item is a sword, it would make sense that it would only be equipable to the left or right hand. If it were a hat, it should only be equipable to the head. So, depending upon what your item is, specify where it can be worn on the body. You can specify more than one location.
Also, you can tell it to be equipable as a Special Accessory. If you check off this box, you then have to fill out which part of the body this can be equipped to. Remember in the character editor when you could create your own custom slots? Well, let’s say you had previously created a slot called ‘Ring Finger’ on your character. Now, you could specify that your item can be equipped to ‘Ring Finger’.
Next, you must specify the effects this item will have on the character when it is equipped. For example, if the item were a sword, then it should increase fighting power (FP). If it were a shield, it would increase defensive power (DP).
The boxes that follow allow you to specify the number of points each characteristic of the character will gain upon equipping the item. Note that when the item is un-equipped, these special effects will be removed as well.
Also, you could make a item, one that damages the character when equipped. These items would have negative increase values. You could also have some sort of item which gives the player lots of FP, but which takes a lot of HP off. This adds a lot more strategy when the player is trying to determine what equipment they will put on their players. *cursed*
Finally, you can have RPGCode programs run when the item is equipped/ un-equipped. For a ‘master sword’, you might have a program run which will do something special when the item is equipped.
**
Menu Driven
![](Image428.jpg)
You can also make the item . This means that you can use the item from the internal menu of the game. This is good for making potions and things, which can heal the player. *Menu Driven*
This is pretty simple. You just have to fill out the amount by which the player’s health and SMP increase when the item is used.
Also, you can have an RPGCode program run when the item is used. This program can be used to make a little sound or something if you like.
Keep in mind that when you use an item from the menu, it is gone. If you want to make an item which doesn’t do away when used from the menu, you can have it use an RPGCode program which uses the #GiveItem command to give the item back after it gets used up.
**
Board Driven
![](Image429.jpg)
This option is probably the most used. If you want to make an NPC (Non-player-character), this is how you do it.
An NPC is just your regular Joe in the game. You know when you play RPG’s and there are stupid little kids running around villages and crazy old men telling you about the time ‘before the Empire took over’? Those are NPC’s.
There are only two things that you have to fill out to make an NPC. First is the program to run while the item is on the board. This is a special type of program called a multi-task program. It’s called this because it runs simultaneously while other programs are also running (other NPC’s) and while the character walks around. This program lets you make the item walk around and do whatever it does on the board.
The Toolkit comes with a program called Wander.prg that causes an NPC to wander around aimlessly. I use it for most of my board driven items. However, you can also write your own RPGCode programs to cause the item to chase the player around, or evade the player.
The other program that you have to declare here is the program that gets run when the item is ‘picked up’. Now, if the item is an NPC, this means ‘when the player talks to the person’. Usually, this program is just used to make the NPC talk to the player (using #Mwin commands). Of course, it can do others things as well.
If your board driven item is an NPC, then you are probably using it to be an actual item that’s just sitting there on the board. When the player picks it up, something happens, or the player gets that item in his inventory. If you want to make an item which you can pick up, just use the #GiveItem command in the ‘Pick up’ program. *not*
The board editor can override both of these programs. When you place an item on the board, you can specify different multitask and pick up programs. This is good, because if you make an NPC with a bunch of movement graphics, you don’t want to have to make a different one for every character in the game.
**
Battle Driven
A battle driven item is almost exactly like a menu driven item, except that it can be used in a fight. The options for creating it are the very same as the menu driven style. Battle driven items may include potions (for healing players) and ‘throwable’ weapons (used against enemies). Battle driven items get used up when used from battle.
Also: If an item is equipable battle driven, and the item is equipped on a player’s right or left hand, then the program that gets run by the battle-driven item will get run each time the player swipes his or her sword (Attacks). In this instance, the item will not get used up, because the player has it equipped. *and*
If your item is to be an NPC, it have graphics. When you click on the ‘Graphics’ button, a window will pop up that is similar to the character editor’s graphics screen. *must*
This window allows you to fill out the walking and at-rest graphics for this item. If your item is board driven and moves around (i.e., it uses programs such as the wander.prg file), it must have graphics (otherwise, how will it walk around?)
***
Other Options
At the bottom of the item menu are a few other options. First of all is a check box that says if the item is a ‘Key Item’ or not. A key item is an item that the player cannot drop or sell. It is an item that you want the player to keep throughout the whole game.
Also, there is a purchase price and a selling price that you can fill out. Items can be bought and sold in shops, and these fields will determine what the going rate is for this item (these shops are called with the #CallShop RPGCode command).
Finally, you can specify exactly who can use this item. By default, all characters can use the item (if it is equipable/menu/battle-driven). However, you may want only certain players to be able to use certain items. If you select ‘Used By Defined Characters’, you can fill out which characters can use this item (up to 50 characters—you must specify their Handles).

Edit Special Move
![](Image430.jpg)
Remember in the Character Editor when you gave the character ‘Special Moves’? Well, here is where you create those special moves.
A special move is a specialized attack that a player can use in a fight. It is usually more powerful and drains a portion of the player’s energy or Special Move Power (SMP).
Special moves can be used for everything from specialized physical attacks to powerful magical attacks. It’s very easy to make a special move…
***
Special Move Stats
The first things you have to fill out are the special move stats. These determine how strong the special move is.
The name of the special move is the name that is sown in the battle menu for the move (negative values make the move a curative move).
The Fight Power is the fighting strength the move has, and the amount of SMP removed from the target is the amount of SMP removed from the enemy against which the special move is being used (usually this is 0).
The SMP consumption is the amount of SMP the special move removes from the player when the player uses the move.
***
Special Effects and Uses
The RPGCode program is a program that is run when the special move is used. This is intended to create special effects when the move is used. For example, let’s say you create special move called ‘Fire’. You could write an RPGCode program to show a fireball moving across the screen. This program would be run before the special move took off damage from the enemy.
Finally, the last two check boxes determine where the special move can be used. Most special moves can be used from a fight. So almost every special move you make should be battle-driven. Also, you can make these moves menu-driven as well, which means they can be used from the game’s internal menu. Curative moves are usually menu-driven also.

Tileset Editor
![](Image431.jpg)
You should use tilesets. The old .gph tiles are fine for getting to know the Toolkit, but you’ll really be doing yourself a favor by using tilesets.
The tileset editor allows you to create and manage tilesets. But before I begin into that, maybe I should tell you how to make tilesets in the simplest way…
***
Creating a tileset with the Tile Editor
The easiest and best way to create a tileset is from the Tile Editor. When you make a tile, when you save it, give it a filename, but add .tst at the end of the name. This will create a new tileset with that filename and add the tile into it.
Whenever you want to add new tiles into that tileset, you just have to save them with the name of the tileset itself (i.e., to save into a tileset called cave.tst, when you went to save each tile, save it as cave.tst). Don’t worry—this won’t save over your tileset, instead, it’ll add the tile you are trying to save into the tileset. Pretty easy stuff.
To open a tile from a tileset, you just have to act as if you are opening a regular tile, but instead of selecting a .gph tile, select a .tst file. This will pop up a widow showing you all the tiles in the set. Just click on the tile you want to open it.
If you do all tileset management with the tile editor, you should be fine. But the Tileset Editor allows you to modify a tileset in more ways.
***
Tileset Editor
The tileset editor allows you to add lots of tiles at once to a tileset. So, if you’ve made lots of .gph tiles, you can put then all into a tileset easily. But first, there are a few things to know about a tileset:
**
Tileset Characteristics
A tileset has a set , just like a tile. Tiles in the Toolkit can be anywhere from 32x32x16.7 million colors all the way down to 16x16x16 colors. A tileset is the same. *detail level*
When you first create a tileset, any tiles you add to it from then on must have exactly the same detail level and color depth. This probably isn’t a problem since most tiles you’ll make will be 32x32x16.7 million colors. But be warned: if you create a tileset by adding a 16x16x256 colors tile into it, tile you add from then on must be 16x16x256 colors. *every*
There is no limit to the size of a tileset. But for your sake, you might want to keep it below 1000 tiles. It doesn’t make any difference in speed for the Toolkit, but it’s easier for us humans to look for an image if it’s not buried along with 1000 other images.
Once you start using tilesets, you’ll probably get addicted to them. I never use .gph tiles anymore, except for very special cases (it’s easier to use .gph tiles in RPGCode, for instance). At the time of writing, tilesets are relatively new to the Toolkit (tileset support only came out 5 months ago), but already there are many tilesets available for Toolkit games, both original and ripped from popular RPG games. You should have no problems finding what you want, and if you can’t find a tileset you want, you can always create one.
Tilesets make importing from other games or game development systems much easier than using .gph tiles. If you ever import graphics from another game on a large scale, you will immediately appreciate the benefits of the tileset.
***
Adding Lots of Files to a Tileset
Let’s say you’ve got 600 .gph tiles made, but you want to put them into a tileset. No problem. The Tileset Editor allows you to do this in two ways…
**
Using the File Filter
The quickest way to put lots of tiles into a tileset is by using the File Filter box at the top of the Tileset Editor window. This lets you specify the conditions under which tiles are added.
You are allowed to use wildcard characters. For example, *.gph will add tiles into the tileset; c*.gph will add all tiles that start with the letter c. *all*
Once you have filled out the filter box, just click on ‘Add Files To Tileset’. You will be asked what tileset you wish to save the tiles into, and then they will be put into the tileset. It’s as easy as that.
**
Adding Files Visually
![](Image432.jpg)
You can also add files one at a tile to a tileset by browsing the available tiles and then placing them into the tileset.
Click on the ‘Add files Visually’ button, and you will first be asked for a filename of a tileset to add files into. Then a new window will pop up.
This window shows you two list boxes. The one on the left shows you all of the .gph tiles that you have. The one on the right shows you all of the tiles that are stored in the selected tileset.
You can add .gph tiles to the tileset by clicking on the filename and hitting the ‘Add ->’ button. You can copy files out of a tileset by clicking on a tileset tile and hitting the ‘<- Copy’ button.
This window also allows you to ‘Remove Duplicate’ .gph tiles from your tiles directory. When you import a screenshot from another game using the Tile Grabber (see tile editor section), it will create a lot of .gph tiles in your directory. Some will be duplicates (since virtually no image is made up entirely of different tiles). You can hit the ‘remove duplicates’ button to have the Toolkit scan all tiles in your tiles folder and remove any duplicates. Be warned: this option will delete files permanently (but if a file is deleted, there will always be another one that is exactly the same).
***
Ripping Tiles
There are lots of great RPG’s out there. Maybe you’d like to make a continuation of your favorite game, or just use the same graphics. Well, you can easily import graphics from any other RPG game using the Toolkit. Here’s how I do it:
>
> I go into the Tile Editor, and select ‘Grab Tiles’.
>
> I open up a screenshot of the game I wish to import (you can capture the screen of any window game by pressing the ‘Print Screen’ button on your keyboard, going into a graphics editor and pasting the image from the clipboard; some DOS programs let you save screenshots; emulated SNES or Genesis games usually have screenshot option in the emulator).
>
> Depending upon where I got the graphic, I use Batch Import (32x32) or Batch Import (16x16) (Most DOS and SNES games use 16x16 tiles, most windows games use 32x32).
>
> I am asked to save my tiles. I usually give the tile grabber a filename like the first two letters of the game I am importing.
>
> Now, the tile grabber will grab all of the tiles on screen. This creates LOTS of .gph tiles.
>
> Now, I go into the Tileset editor and hit ‘Add files visually’
>
> I give it some filename.
>
> Now I hit ‘remove duplicates’. This will remove duplicate tiles from the screen grab.
>
> Next, I will add the tiles one by one to my tileset visually, or I’ll just go out and add them with the file filter option (much faster), by using ab*.gph, where ab are the first two letters I chose before.
>
> Finally, I browse the tileset to make sure everything is OK, then I delete the .gph tiles that were created by the Tile grabber (go into DOS and type del ab*.gph, where ab is the first two letters).
>
***
Using Tilesets from RPGCode
Tilesets are a little clumsy in RPGCode, but usable. I usually still use .gph tiles in RPGCode, because their filenames are more descriptive. Here’s an example:
In RPGCode, I could type:
#Put(1,1,"grass.gph")
To put a grass tile at 1,1. But let’s say my grass tile is saved in a tileset and it’s the 18 tile in that tileset. Here’s how I would use the same command: th
#Put(1,1,"tilesetfilename.tst18")
The 18 tile in a tileset called tilesetfilename.tst is referred to by tilesetfilename.tst18. Pretty easy. th

Make it Work
Sometimes you may be playing a game and your character will move to the edge of the board and will not be able to move onto the next board. When this happens, there may be a number of reasons: This happens when your player does not have graphics, or you have not set the initial board position. To fix this, give the character graphics, or go to the Board Editor, and set the player position. You may be pressing the wrong key. Check the Main File in the Main File Editor to see which key is correct. Also, the filename of the program may not exist, or the program may not do anything in the first place. In this situation, check the program itself to see what it actually does. Sometimes including a little #MWin statement at the very first of the runtime program will allow you to at least see if the runtime program is being run each time you try it. This is by far the worst problem you will encounter. Programs are rarely perfect the first time they are run. Usually, if there is a problem with the way you use a command, the Translator will tell you what the problem is when you run the program. This is one of the hardest problems to fix because there is no cut and dry method of determining if the program is doing something wrong. In almost every case, lock ups are due to mistakes in RPGCode. You will probably find that lock ups only occur when you run a program. This is easily fixed. No game is perfect on its first run. Even professionals hire people to play their games to find all the mistakes they’ve made. The RPG Toolkit eliminates many of these bugs by having much of the players’ actions already coded and debugged. Setting Up a Game For Distribution
![](Image444.jpg)
Once you have a game made, you’ll probably want to make it available to other people to play.
Before you make your setup program, you may want to delete unneeded files (i.e., the demo game), since the setup program will copy everything that is under the Toolkit2 directory.
The Toolkit comes with a Setup Kit program that will create a setup file for you. You can run this program by hitting the ‘Create Setup’ button in the Toolkit, or by running setupkit.exe. Before you run it, you will have to do this, though:
>
> >
> > >
> > > Setupkit.exe requires pkzip version 2.5 in order to work. You can download the shareware version of pkzip from the RPG Toolkit website (http://rpgtoolkit.pyar.com), or from pkware’s website (http://www.pkware.com).
> > >
> > > Once you have the pkzip25.exe program, copy it into your c:\toolkit2\zip directory.
> > >
> > > Now you’re all set! Just run setupkit.exe
> > >
> >
>
The setupkit program has a few things to fill out. First is the title of your game. This is pretty straightforward.
The default directory for your game is the location where you would like your game to be installed on another computer.
The location of your windows system directory is almost always c:\windows\system. You can leave this field alone.
The location of your Toolkit directory is probably c:\toolkit2. If it is not, specify the directory location.
Once you have this information filled out, hit the ‘Create Setup Program!’ button and follow the directions onscreen. When all is said and done, you will have a .zip file sitting on your computer that contains your game and a setup program for your game. I suggest you test out the setup program before distributing the game.
